== Design Decision — GNPL vs LithoglyphDB (Not Mechanical)

This is a *design decision*, not a mechanical file move. The two have distinct
semantic purposes:

[cols="1,1,3", options="header"]
|===
| Aspect | LithoglyphDB | GNPL

| *Purpose* | Narrative-first, reversible, audit-grade database — stores journals, entities, proofs, with temporal reversibility and audit trail
| GQL-dt / GNPL — narration/projection language: "what account does this evidence support?" Constructs accounts from evidence with stances, warrants, rival interpretations

| *Layer* | Storage / persistence / journal / proof registry (Zig core, Elixir HTTP, Rust NIF)
| Language / query / narration: typed selection, storage machinery (private impl), account construction, focalization, hypothetical withdrawal

| *Proof* | Unimplemented builtin verifiers refuse success; registered callback plumbing has positive/rejection controls (per EXPLAINME.adoc 2026-09-07)
| Independent direct-evidence narration kernel and CLI; 5 Lean suites (35 narration checks); withdrawal/order properties audited for [propext] footprint

| *API* | Journal, entity, proof registry, reversibility
| Narration: accounts, focalization, warrants, limited rival relation, hypothetical withdrawal — lowers to GQLdt
|===

*Why separate?*

- LithoglyphDB can exist without GNPL (other query languages can target its journal)
- GNPL can exist without LithoglyphDB (uses imported snapshots + direct-evidence warrants today; live Lithoglyph adapter remains work per STATE.a2ml)
- Their proof obligations differ: Lithoglyph needs verifier integration; GNPL needs narration correctness + withdrawal properties
- Their public language is GNPL (one of four: VCL-UT, GNPL, KRL, Hermeneia) — not "Lithoglyph query language"

*What was superseded, not migrated:*

- `lithoglyph/core-factor/gql/` — runtime/dynamic counterpart to GQLdt's compile-time proofs. A typed narration layer lowering to GQLdt replaces it, so it was never migrated and should not be "finished". See `lithoglyph/README.adoc` and `docs/migration/RESITE-DATABASES-TO-OWN-REPOS.adoc`.

== Glyphbase — Own Repo, Owner-Decided

Glyphbase is an application surface (AirTable-like app) over LithoglyphDB, with Grid/Kanban/Calendar/Form/Gallery views + stores + bindings (Yjs/Jotai/Webapi/Fetch).

- *Why own repo?* UI concerns (bindings, stores, view logic) differ from core DB concerns (journal, reversibility, audit). Owner decides UI stack (AffineScript TEA per migration plan, mirroring `quandledb/frontend` + `nqc`).
- *Extraction:* Un-nested from `lithoglyph/glyphbase/` → `hyperpolymath/glyphbase`
- *Status:* DONE (see `lithoglyph/README.adoc` Where each part went table)
